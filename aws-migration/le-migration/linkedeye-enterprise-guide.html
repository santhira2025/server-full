Platform Overview

LinkedEye is FinSpot Technology Solutions' shared ITSM/Monitoring platform deployed on AWS. It serves 16 enterprise clients with dedicated Kubernetes namespaces, on-premise hybrid worker nodes, and centralized management tools including Jenkins, Harbor, ArgoCD, Keycloak, Vault, and ITSM portal.

24
K8s Namespaces

Key Features

  • EKS Hybrid Nodes — AWS-managed control plane, on-prem workers per client
  • Multi-tenant isolation — NetworkPolicy + RBAC + ResourceQuota per namespace
  • Zero VPN required — Hybrid nodes connect via public EKS API (HTTPS 443)
  • GitOps CI/CD — Jenkins + Harbor + ArgoCD pipeline
  • Centralized SSO — Keycloak for all tools authentication
  • Secret management — HashiCorp Vault with per-client paths
  • HA architecture — 2 AZs, single NAT GW, 2 nodes per client
  • TLS everywhere — ALB with ACM wildcard cert (*.finspot.in)

Per-Client Namespace Isolation (5 Layers)

1

NetworkPolicy (Network Isolation)

Each namespace only allows ingress from itself and le-monitoring. All egress allowed. Prevents cross-client pod communication.

spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels: { kubernetes.io/metadata.name: le-{client}-prod }
    - namespaceSelector:
        matchLabels: { kubernetes.io/metadata.name: le-monitoring }
2

ResourceQuota (Resource Limits)

Hard limits per namespace prevent one client from consuming all cluster resources.

Production:  requests.cpu=4, requests.memory=8Gi, limits.cpu=8, limits.memory=16Gi, pods=20, PVCs=5
Non-Prod:    requests.cpu=2, requests.memory=4Gi, limits.cpu=4, limits.memory=8Gi, pods=10
3

LimitRange (Default Pod Limits)

Containers without explicit resource requests get sensible defaults.

Default Request: 100m CPU, 128Mi Memory
Default Limit:   500m CPU, 512Mi Memory
4

RBAC (Access Control)

Two RoleBindings per namespace for least-privilege access.

le-client-admin:     Group "{client}-admins" can manage pods, deployments, services, secrets
le-argocd-deployer:  ServiceAccount "argocd-deployer" has full namespace access for GitOps
5

Node Affinity + Taints (Workload Placement)

Pods are scheduled only on the client's on-prem hybrid nodes via nodeSelector + tolerations.

nodeSelector:   { client: indmoney }         # Only match this client's nodes
tolerations:    [{ key: client, value: indmoney, effect: NoSchedule }]
Node taint:     client=indmoney:NoSchedule   # Reject pods without toleration

Hybrid Node Registration (On-Prem Workers)

How Hybrid Nodes Work

EKS Hybrid Nodes let on-premise servers join an AWS EKS cluster as worker nodes. The control plane stays in AWS, workers run at client sites. Communication is via HTTPS 443 (outbound only) — no VPN required.

Registration Flow (Per Client)

STEP 1: Admin creates SSM Hybrid Activation in AWS Admin PC ---> aws ssm create-activation --iam-role linkedeye-hybrid-node-role | v Returns: Activation ID + Code (Valid for 24 hours, max 2 registrations) STEP 2: Install SSM Agent on on-prem server Client Server ---> sudo apt install amazon-ssm-agent ---> sudo amazon-ssm-agent -register \ -id "ACTIVATION_ID" \ -code "ACTIVATION_CODE" \ -region ap-south-1 | v Server registered as mi-0xxxxxxxxx (Managed Instance in SSM) STEP 3: Install nodeadm and bootstrap to EKS Client Server ---> sudo nodeadm install 1.31 --credential-provider ssm ---> sudo cat > /etc/eks/nodeadm-config.yaml apiVersion: node.eks.aws/v1alpha1 kind: NodeConfig spec: cluster: name: linkedeye-finspot-k8s-cluster region: ap-south-1 hybrid: ssm: activationId: "..." activationCode: "..." ---> sudo nodeadm init | v Node joins EKS cluster kubectl get nodes shows: mi-0xxx Ready STEP 4: Label and taint the node Admin PC ---> kubectl label node mi-0xxx \ client=indmoney \ node-type=hybrid \ topology.kubernetes.io/zone=client-indmoney ---> kubectl taint node mi-0xxx \ client=indmoney:NoSchedule

Worker Node Startup Flow (Why Each Service is Needed)

STEP 1: NODE REGISTRATION Worker Node ---> SSM (#3,4,5) Node tells AWS "I exist" and gets an identity Without this: Node cannot register, invisible to AWS STEP 2: AUTHENTICATION Worker Node ---> STS (#6) Node gets temporary IAM credentials (refreshed every 12 hrs) Without this: Node loses auth, pods stop scheduling STEP 3: JOIN CLUSTER Worker Node ---> EKS API (#1,2) kubelet connects to Kubernetes control plane Without this: Node cannot join cluster, no pods run STEP 4: PULL SYSTEM CONTAINERS Worker Node ---> ECR + S3 (#7,8,9,10) Downloads Kubernetes system components (kube-proxy, vpc-cni) Without this: Node starts but system pods fail STEP 5: PULL APP CONTAINERS Worker Node ---> Harbor (#11) Downloads ITSM and monitoring application images Without this: App pods fail with ImagePullBackOff STEP 6: ACCESS ITSM PORTAL Worker Node ---> ALB (#12,13) Pods communicate with ITSM management platform Without this: Monitoring/alerting doesn't work RESULT: Node is READY, pods running, client monitored

Security Architecture

SECURITY LAYERS Layer 1: NETWORK +-- ALB with TLS 1.3 (ELBSecurityPolicy-TLS13-1-2-2021-06) +-- Security Groups (5 groups, least-privilege rules) +-- NetworkPolicy per namespace (K8s level isolation) +-- Private subnets for EKS control plane ENIs +-- No inbound to on-prem (outbound HTTPS only) Layer 2: IDENTITY +-- Keycloak SSO (OIDC/SAML for all tools) +-- IAM Roles (EKS cluster role, node role, EC2 role) +-- RBAC ClusterRoles (le-client-admin, le-argocd-deployer) +-- Per-namespace RoleBindings (group-based) +-- Pod Security Standards (baseline enforce, restricted warn) Layer 3: SECRETS +-- HashiCorp Vault (per-client paths: secret/le-{client}-prod/*) +-- SSH key: le-shared-k8s-key.pem (single key for EC2 access) +-- EKS OIDC for pod IAM roles (IRSA) Layer 4: SUPPLY CHAIN +-- Harbor image scanning (Trivy) +-- Image signing (Notary) +-- Jenkins pipeline validation +-- ArgoCD sync policies (manual for prod) Layer 5: RUNTIME +-- ResourceQuota per namespace (prevent resource abuse) +-- LimitRange defaults (container resource limits) +-- Node taints (workload isolation per client) +-- PriorityClasses (scheduling priority) Layer 6: MONITORING (Phase E - Pending) +-- AWS GuardDuty (threat detection) +-- AWS WAF (ALB web application firewall) +-- AWS CloudTrail (API audit logs) +-- VPC Flow Logs +-- Prometheus + Alertmanager (K8s monitoring)
